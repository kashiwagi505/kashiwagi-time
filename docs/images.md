### 命名の約束（他の担当との契約）

- `chara/<役名>.png` … 役名は **Javaクラス名の小文字**（`hero` / `wizard` / `tank` / `archer`）。
  クラスの無いキャラは日本語の役名の英字表記（`saint` / `assassin` / `priest` / `maou`）。
- `<名前>.png` = 原寸ロスレス（拡大表示 F10 用のマスター）
- `<名前>.webp` = 原寸の軽量版（**ページ本文で使うのはこちら**）
- `<名前>-320.webp` = カード内サムネイル用（長辺320px）
- `figures/` だけは `-1000` / `-700` の幅指定サフィックス（透過が要らないので寸法基準にした）

## 4. 透過処理の方法

元の背景は**2種類**あった。処理も2系統に分けている。

| 元素材 | 背景 | 方式 |
|---|---|---|
| `image/*.jpg` 6点 | **白**（純白ではなく 249〜255 の揺らぎあり） | 輝度・彩度による白抜き |
| `image/生成画像*.png` 4点 | **マゼンタ**（≒#F704F8。クロマキー） | 緑の落ち込み量によるキーイング＋スピル除去 |
| pptx由来 `chara_*.png` | すでに透過済み | 再処理せずそのまま（`passthrough`） |

### 手順（`make-transparent.js`）

1. 画素ごとに「背景らしさ」を 0〜1 で計算する
   - 白: `min(r,g,b)` が高く `max-min` が小さいほど背景（234→249 で連続的に変化させる）
   - マゼンタ: `min(r,b) - g`（緑の落ち込み）が大きいほど背景（70→170 で連続変化）。
     さらに `min(r,b)` が 150→195 の範囲でなだらかに効かせる
2. **外周からフラッドフィル**して「外から到達できる背景」だけをマスクにする。
   → 白目・白い装備・ハイライトなどキャラ内部の白に穴があかない
3. **内包された背景を統計量で救済**する。フラッドフィルだけでは
   弓使いの弓の内側・魔法使いの腕と杖に囲まれた領域・魔王のマントの破れ穴が残る。
   外周背景との平均差と分散で、内包された**前景**（聖女のヴェールの折り目、魔法陣の紫の宝石）と
   区別している。実測値の分離は明確だった:

   | 内包領域 | 平均差 | 分散 | 判定 |
   |---|---|---|---|
   | 弓の内側（背景） | -0.2 | 1.7 | 抜く |
   | 聖女のヴェール（前景） | -1.6 | 3.1 | 残す |
   | 魔王のマントの穴（背景） | -12 | 15 | 抜く |
   | 魔法陣の紫の宝石（前景） | **-155** | 9 | 残す |
4. マスクを2〜3px膨張させ、境界の中間色画素まで alpha を連続値にする（ジャギー・白縁対策）
5. マゼンタはスピル（輪郭のピンクにじみ）を despill で抑える
6. `alpha=0` の余白を trim してタイトに切る

### 原本 1254px を採用した（pptx由来600px版は使わなかった）

`cross-session-findings.md` と `extracted/images/README.md` は
「pptx内の透過PNGをそのまま使えば白背景問題は解決する」としていたが、**採用しなかった。**

| | 原本から生成（採用） | pptx由来600px版 |
|---|---|---|
| 寸法 | 1023〜1182 × 1054〜1233 | 長辺600px |
| 拡大表示(F10) | 対応できる | **足りない** |
| 縁の品質 | 白残り 0.0〜0.1%（下記の数値点検） | 同等（元から透過） |

**判断根拠: 品質が同等で解像度が2倍以上あるため。** `qa-edges.js` で輪郭画素の白残りを
測ったところ、原本から生成した5点は 0.0〜0.1% で、pptx由来版（0.0%）と実用上の差が無かった。
目視でも穴・白縁・ピンク縁は確認できなかった（藍・緑・赤の3色の背景に載せて確認）。

**`assassin` / `priest` / `holy-sword-slide` の3点だけは pptx由来600px版を使っている。**
`image/` に原本が無いため。**この3点は拡大表示すると粗い**（6章）。

## 5. 再実行のしかた

```
cd site/tools
npm install              # sharp をローカルに入れる（初回のみ）

node make-transparent.js         # 立ち絵・アイテムの透過＋WebP変換（全部）
node make-transparent.js hero maou   # キーを指定して一部だけ
node make-silhouette.js --compare    # シルエット4案の比較シートを出す
node make-silhouette.js              # 採用案を出力
node make-figures.js                 # 第2回の概念イラストをWebP変換
```

### 点検用

```
node qa-edges.js                          # 輪郭の白残り／マゼンタ残りを数値で点検
node qa-sheet.js "#1a237e" chara/hero.png chara/maou.png ...   # 色背景に並べた確認シート
node qa-zoom.js chara/saint.png "#1a237e" 330 880 120 7        # 部分を等倍拡大して確認
node inventory.js ../../image ../../00_research/01_inventory/extracted/images  # 元素材の棚卸し
node analyze-bg.js ../../image/warrior.jpg    # 背景色の実測（閾値を決め直すとき）
node comp2.js ../../image/saint.jpg           # 内包領域の統計（救済の閾値を決め直すとき）
```

### ⚠ `sharp` はグローバルには入っていない

`CLAUDE.md` 6章は「グローバルnpm: `jszip` / `sharp` / `pptxgenjs` / `exceljs` / `corepack`」と
書いているが、**2026-07-31 時点で `npm root -g` にあるのは `@openai` / `corepack` / `npm` だけ**で
`sharp` も `jszip` も無かった。`site/tools/package.json` でローカルに入れる方式にしてある
（`npm install` は成功。registry には到達できる）。

### 容量

| 区分 | 容量 |
|---|---|
| PNG 原寸マスター（13点） | **17.0MB** |
| WebP 原寸（13点） | 2.1MB |
| 縮小版（320/700/1000px 計） | 0.5MB |
| **合計** | **19.7MB** |

- 変換前の元素材は 13.8MB（`image/` 10点 9.7MB ＋ pptx由来6点 4.1MB）。
- **`figures/` は 3.0MB(PNG 3点) → 97KB(WebP原寸 3点) = 約3%** に減った。
  フラットなベクター調イラストのため WebP が非常によく効く（`figures/` 全体は3サイズ計で204KB）。
- **PNG マスターが全体の86%を占めている。** ページから参照するのは WebP だけなので、
  **PNG を GitHub Pages の公開物に含めるかは要判断。** WebP だけなら 2.6MB で済む。
  `.eleventy.js` は現在 `addPassthroughCopy({ "src/assets": "assets" })` で
  `src/assets` を丸ごとコピーしているので、**このままだと PNG 17MB がそのまま公開される。**
  PNG を残すならロスレスのマスター置き場として `_masters/` などに分け、passthrough 対象から
  外す構成を勧める（→ サイト構成の担当と調整が必要）。
- PNG は `adaptiveFiltering: true` でロスレスに約20%圧縮してある
  （`effort: 10` は256色パレットに量子化されて劣化したので使っていない）。
